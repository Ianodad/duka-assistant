# Duka Assistant: Week 1 SPEC

Goal: a Next.js server-rendered shop (catalog, cart, Daraja STK Push checkout) that runs locally. Week 1 only. Weeks 2 to 4 (A2UI panel, WebMCP tools, hardening) are NOT built now; see PLAN.md.

Sources: Rada's research /workspace/research/a2ui-webmcp-ecommerce/2026-11-20-report.md. UI reused (copied, never modified) from /workspace/projects/duka-assistant-spike at ec42273 (Tailwind 4, lucide-react, cva, clsx, tailwind-merge, Bricolage Grotesque). Enroll's Daraja module (/workspace/enroll-phase-3/packages/adapters/payments/daraja) is read-only reference; it refuses all wire fields by design, so Duka has its own small client built on the publicly documented Daraja sandbox endpoints.

## Acceptance criteria

- AC-1 Project: /workspace/duka-assistant, Next.js App Router, TypeScript strict, local git only (no remote). Installs only inside the project. Dev/start port 3200.
- AC-2 Catalog: server-rendered catalog page (/) and product detail page (/p/[slug]) with at least 8 products, prices in KES (integer shillings). Product HTML is present in the initial server response (no client-only render).
- AC-3 Cart: add, change quantity, remove, subtotal. Cart state is held server side (cookie session id plus server store) so the server, not the client, computes totals. Cart page /cart.
- AC-4 Checkout page /checkout: shows order summary and a Kenyan phone input. Phone normalised to 2547XXXXXXXX or 2541XXXXXXXX; invalid numbers rejected with a clear message.
- AC-5 Pay tap only: STK Push is triggered ONLY by the shopper pressing Pay on /checkout, through one server action (or one POST route) that requires a same-origin request and a server-issued per-checkout token. No other route, server action, API, script hook, or agent/tool path can call the STK initiation function. Enforced by code structure (a single caller) and by tests.
- AC-6 Orders: an order is created from the server cart at Pay time with the amount computed server side. States: pending, paid, failed, cancelled. Only allowed transitions: pending to paid, pending to failed, pending to cancelled. Terminal states never change. Idempotent: duplicate callbacks or queries do not change a terminal order.
- AC-7 Status query: the order page /orders/[id] shows the state and polls a status endpoint; while pending the server may run the Daraja STK query (sandbox) or mock query. Status endpoint is read and reconcile only; it can never start an STK push.
- AC-8 Callback route POST /api/daraja/callback: parses the STK callback body, matches by CheckoutRequestID, maps ResultCode 0 to paid, 1032 to cancelled, other codes to failed. Validates shape, rejects unknown CheckoutRequestID without changing anything, returns a 200 JSON ack. Optional shared secret in callback URL path/query when configured.
- AC-9 Adapter modes: DarajaAdapter interface with mock mode (DEFAULT) and sandbox mode. Mode selected by DUKA_DARAJA_MODE (mock | sandbox, default mock). Mock mode never touches the network and simulates outcomes deterministically (for example by phone suffix or a test control) including pending, paid, failed, cancelled.
- AC-10 Sandbox env: sandbox mode reads its env from the file at DUKA_DARAJA_ENV_FILE (default ~/.secrets/duka-daraja-sandbox.env). Variables: DARAJA_ENV, DARAJA_CONSUMER_KEY, DARAJA_CONSUMER_SECRET, DARAJA_SHORTCODE, DARAJA_PASSKEY, DARAJA_CALLBACK_URL (optional). Refuses to start sandbox mode if DARAJA_ENV is not "sandbox" or the base URL is not the sandbox host. Never reads the Enroll env file, enroll-daraja-sandbox.env (explicit refusal of that file name). Missing file or vars gives a clear error naming the missing variable names only.
- AC-11 Secrets: no secret in the repo, logs, errors, or responses. A redact() helper masks consumer key, secret, passkey, password, access token and Authorization headers; used for every log line from the adapter. .env.example has placeholders only. A secret-scan test greps the repo (excluding node_modules, .next) for key-like strings.
- AC-12 Sandbox smoke script scripts/sandbox-smoke.ts (run with the project's tsx or node --experimental-strip-types): OAuth token, one STK push for a small amount (KES 1) to a phone given by argument, then the STK query; all output redacted. It is NOT run in this build (no Duka keys exist). It must exit with a clear message if the env file is missing.
- AC-13 UI: reuses the spike's visual language (Tailwind 4, Bricolage Grotesque, lucide icons, cva buttons). Responsive at 390px and 1280px with no horizontal overflow. Accessible labels on inputs and buttons.
- AC-14 Tests: unit tests (vitest) for cart math, phone normalisation, order state machine, callback mapping, redaction, env loader (including refusal of the Enroll env path), adapter mock mode, sandbox adapter request shapes with a fake fetch (no network). A guard test proving no non-checkout path can trigger STK: (a) static scan that only the checkout pay action imports/calls initiateStk, (b) runtime tests that GET/POST to every other route (status, callback, cart, catalog) never call the adapter's initiate method.
- AC-15 E2E: Playwright (a vendored Playwright, path set by DUKA_PLAYWRIGHT_PATH, no global install) against a production build in mock mode: browse catalog, add to cart, change qty, checkout, pay tap, pending state, then paid; also a failed or cancelled path. Screenshots to evidence/week1/: catalog.png, cart.png, checkout.png, pending.png, paid.png (plus mobile variants welcome).
- AC-16 Docs: README.md (run commands, modes, env vars by name only), NOTES in PLAN.md with weeks 2 to 4 estimate in days. No em dashes anywhere.
